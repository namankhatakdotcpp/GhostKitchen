\section{Audit Scope \& Methodology}
% =============================================================================

\subsection{Scope}

The audit covered the full \texttt{food-delivery-backend} service and the
\texttt{ghost-kitchen-frontend} Next.js application.  Specifically examined:

\begin{itemize}[leftmargin=*]
  \item Error tracking via \textbf{Sentry} (\texttt{@sentry/node}, \texttt{@sentry/nextjs})
  \item Structured logging via \textbf{Winston}
  \item HTTP request tracing and correlation identifiers
  \item Health and readiness endpoints (\texttt{/health}, \texttt{/health/extended})
  \item Incident auto-detection, escalation, and notification pipelines
  \item Operational dashboards (Admin, Ops, Exec)
  \item Background job observability (incident engine, housekeeping, maintenance cron)
  \item Redis and PostgreSQL failure behaviour
  \item Alert coverage matrix
  \item Production runbooks
\end{itemize}

\subsection{Methodology}

Each phase consisted of three steps:
\begin{enumerate}[leftmargin=*]
  \item \textbf{Read} — full source audit of all relevant files
  \item \textbf{Gap analysis} — compare current state against best-practice baseline
  \item \textbf{Remediate or document} — fix in-sprint or record as accepted risk
\end{enumerate}

Severity ratings follow the standard four-level scale:
\textbf{\color{crit}CRITICAL} · \textbf{\color{warn}HIGH} · \textbf{\color{info}MEDIUM} · \textbf{\color{ok}LOW}.

\bottomrule

\subsection{Fixes Implemented}

\subsubsection{Release tag}

\begin{lstlisting}[language=JavaScript,caption={src/config/sentry.js — release tag}]
Sentry.init({
  dsn,
  environment: env.NODE_ENV,
  release: process.env.SENTRY_RELEASE
       || process.env.RENDER_GIT_COMMIT
       || "unknown",
  ...
});
\end{lstlisting}

\texttt{RENDER\_GIT\_COMMIT} is injected automatically on every Render deploy,
giving each Sentry event a direct link to the exact commit that produced it.

\subsubsection{RequestId and userId correlation}

\begin{lstlisting}[language=JavaScript,caption={captureException now tags both IDs}]
export function captureException(err, context = {}) {
  Sentry.withScope((scope) => {
    for (const [k, v] of Object.entries(context))
      scope.setExtra(k, v);
    if (context.requestId) scope.setTag("requestId", context.requestId);
    if (context.userId)    scope.setUser({ id: context.userId });
    Sentry.captureException(err);
  });
}
\end{lstlisting}

The \texttt{globalErrorHandler} was updated to forward \texttt{req.id} and
\texttt{req.user?.id} to every \texttt{captureException} call, creating a
three-way correlation: \texttt{X-Request-ID} header → Winston log line →
Sentry event.

\subsubsection{Cron job error capture}

All three background jobs (\texttt{incident.job}, \texttt{orderTimeout.job},
maintenance cron in \texttt{server.js}) now call \texttt{captureException} in
their catch blocks in addition to logging.

\subsection{Accepted Risk: Frontend server config}

The Next.js \texttt{sentry.server.config.ts} is minimal (no user context, no
integrations beyond the default).  Server-side rendering errors are still
captured; the gap is enhanced breadcrumbs.  Accepted because SSR errors are
rare on this architecture and Vercel already logs them independently.

\texttt{userId} absent from HTTP access log & \cellinfo{MEDIUM} & \cellok{FIXED} \\

\bottomrule
\end{longtable}

\subsection{Fixes Implemented}

\subsubsection{Production-JSON console format}

Winston's console transport now emits pure JSON when
\texttt{NODE\_ENV=production}, making every log line directly parseable by
Render's log aggregator, DataDog, or any ELK-family ingestor.

\begin{lstlisting}[language=JavaScript,caption={logger.js — conditional format}]
const consoleFormat = isProduction
  ? winston.format.combine(
      winston.format.timestamp(),
      winston.format.errors({ stack: true }),
      winston.format.json()
    )
  : winston.format.combine(
      winston.format.colorize(),
      winston.format.printf(({ level, message, ...meta }) => ...)
    );
\end{lstlisting}

\subsubsection{Structured HTTP access log}

\texttt{requestTracingMiddleware} was promoted from a commented-out stub to a
full structured access logger emitting at \texttt{info} level on every
\texttt{res.finish} event:

\begin{lstlisting}[language=JavaScript,caption={requestTracing.middleware.js}]
res.set("X-Request-ID", req.id);

res.on("finish", () => {
  if (req.path === "/health" && res.statusCode < 400) return; // suppress noise
  const level = res.statusCode >= 500 ? "error"
              : res.statusCode >= 400 ? "warn"
              : "info";
  logger.log(level, "http", {
    requestId: req.id,   method: req.method,
    path:      req.path, statusCode: res.statusCode,
    durationMs: Date.now() - req.startTime,
    ip:        req.ip,
    userAgent: req.get("user-agent"),
    userId:    req.user?.id ?? null,
  });
});
\end{lstlisting}

Log line example (production JSON):
\begin{lstlisting}[caption={Sample production log output}]
{"level":"info","message":"http","requestId":"9f3b...","method":"POST",
 "path":"/api/orders","statusCode":201,"durationMs":142,"ip":"103.x.x.x",
 "userId":"cuid2abc","service":"ghostkitchen-backend","timestamp":"..."}
\end{lstlisting}

\section{Phase 4 — Incident Response Readiness}
% =============================================================================

\subsection{Incident Pipeline Review}

The platform has a mature automated incident pipeline:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Auto-detection} (\texttt{runAutoIncidents}) — runs every 2 minutes,
        creates \texttt{OPEN} incident records for anomalous conditions (e.g.\ order
        stuck, agent overdue).
  \item \textbf{Escalation} (\texttt{runEscalations}) — same cadence; promotes
        incidents to \texttt{HIGH}/\texttt{CRITICAL} after configurable thresholds;
        sends admin email at 3 h.
  \item \textbf{Timeline logging} (\texttt{logIncidentEvent}) — immutable audit trail
        for every state transition.
  \item \textbf{Notification broadcast} — \texttt{socket.IO} real-time push to admin
        room + Resend email.
\end{enumerate}

\subsection{Gap Closed: Cron Errors to Sentry}

Prior to this audit, a crash inside \texttt{runAutoIncidents} would log
\texttt{logger.error("Incident engine error")} but produce \emph{no} Sentry event.
Oncall would see the symptom (no new incidents despite anomalous platform state)
without an alert.  All three cron jobs now call \texttt{captureException} in
their catch blocks.

\subsection{Remaining Gaps}

\section{Phase 8 — Production Runbooks}
% =============================================================================

\subsection{Runbook 1: Service Returns 503}

\begin{tcolorbox}[colback=crit!5,colframe=crit,title=\textbf{Trigger: /health returns 503 DOWN}]
\begin{enumerate}[leftmargin=*,nosep]
  \item Check Render dashboard → \textbf{Events} tab for recent deploy failures.
  \item Query \texttt{/health} JSON — inspect \texttt{db.message} for the Prisma error.
  \item If DB is down: check Neon/Supabase dashboard for connectivity; verify
        \texttt{DATABASE\_URL} env var on Render.
  \item If deploy rollback needed: Render → \textbf{Deploys} → select last good SHA
        → \textbf{Rollback}.
  \item Once DB is restored, Render health-check resumes and traffic is restored.
\end{enumerate}
\end{tcolorbox}

\subsection{Runbook 2: Redis Unavailable (DEGRADED)}

\begin{tcolorbox}[colback=warn!8,colframe=warn,title=\textbf{Trigger: /health returns DEGRADED}]
\begin{enumerate}[leftmargin=*,nosep]
  \item Confirm Redis by checking \texttt{/health} JSON → \texttt{redis.status}.
  \item Check Upstash console for quota, connection limits, or region outage.
  \item Immediate impact: rate limiters fall back to in-process; cron locks fail-open
        (incident engine may run on every instance — idempotent but noisy).
  \item Resolution: Upstash auto-recovers; no action needed on Render.
  \item Post-incident: review duplicate incidents created during outage window.
\end{enumerate}
\end{tcolorbox}

\subsection{Runbook 3: Payment Failures Spike}

\begin{tcolorbox}[colback=warn!8,colframe=warn,title=\textbf{Trigger: Sentry alert — 5xx on /api/payments}]
\begin{enumerate}[leftmargin=*,nosep]
  \item Check Sentry event — look for \texttt{cashfree-pg} SDK error message.
  \item Check Cashfree status page (\texttt{status.cashfree.com}).
  \item If SDK error references \texttt{axios} — verify \texttt{npm overrides} for
        \texttt{axios\^{}1.17.0} is deployed (regression check: \texttt{npm ls axios}).
  \item If HMAC failures — verify \texttt{CASHFREE\_SECRET\_KEY} env var on Render
        matches the key in Cashfree dashboard.
  \item Manual refund trigger: \texttt{POST /api/payments/refund/:orderId} with admin JWT.
\end{enumerate}
\end{tcolorbox}

\subsection{Runbook 4: CRITICAL Incident Not Escalating}

\begin{tcolorbox}[colback=crit!5,colframe=crit,title=\textbf{Trigger: Ops team sees CRITICAL incident with no email}]
\begin{enumerate}[leftmargin=*,nosep]
  \item Check Sentry for \texttt{"Incident engine error"} events — cron may be crashing.
  \item Verify \texttt{/health/extended} → \texttt{jobs.incidentEngine.lastError}.
  \item Verify \texttt{RESEND\_API\_KEY} env var on Render is set and not expired.
  \item Confirm admin users have \texttt{email} field populated in DB
        (\texttt{prisma studio} or direct query).
  \item Manual escalation: update incident \texttt{status} to ESCALATED via admin UI.
\end{enumerate}
\end{tcolorbox}

\subsection{Runbook 5: Socket Adapter Downgrade}

\begin{tcolorbox}[colback=info!8,colframe=info,title=\textbf{Trigger: /health/extended shows adapterType: in-memory}]
\begin{enumerate}[leftmargin=*,nosep]
  \item This indicates the Redis adapter failed to initialise — Socket.IO is using
        in-process pub/sub, so events do NOT propagate across backend instances.
  \item Impact: order tracking, live map, and notifications only work for users
        connected to the same backend instance.
  \item Check logs for \texttt{"Socket initialization failed"} at startup.
  \item Verify \texttt{REDIS\_URL} on Render.  Restart the service after correcting.
  \item With a single Render instance, this is lower-impact; with multiple
        instances, prioritise immediately.
\end{enumerate}
\end{tcolorbox}
